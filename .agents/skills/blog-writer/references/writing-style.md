# CloudRumble Writing Style Guide

Style patterns extracted from existing CloudRumble blog posts.

## Voice & Tone Characteristics

### Direct and Conversational
- Write like talking to a competent colleague
- Use "you" to address reader directly
- Ask rhetorical questions to engage
- Share personal perspective: "I built", "I use", "Let me show you"

### Problem-Focused Opening
Start with the reader's problem, not your solution:
- ✅ "You ask an AI to generate a manifest. You apply it. Nothing works."
- ❌ "This blog post will teach you about AI validation tools."

### Confident but Not Arrogant
- Make definitive statements: "This works" not "This might work"
- Back claims with data or examples
- Acknowledge limitations when relevant
- Invite feedback and discussion

## Sentence Structure Patterns

### Length Variation
Mix short punchy sentences with longer explanatory ones:

**Short (impact):**
- "Nothing works."
- "Try it now."
- "That's it."
- "The result? Teams stop trusting AI."

**Medium (standard):**
- "This isn't a bug—it's AI hallucination." (8 words)
- "The AI knows YAML syntax but hallucinates config options." (10 words)

**Long (explanation):**
- "Platform teams produce and maintain the infrastructure and services that all of your teams use to communicate with each other and perform tasks." (24 words)

**Pattern:** Short for emphasis, medium for standard, long for complex ideas. Never more than 3 long sentences in a row.

### Active Voice Dominance
- ✅ "AI generates configs"
- ❌ "Configs are generated by AI"
- ✅ "Teams stop trusting AI"
- ❌ "AI trust is lost by teams"

Use passive only when actor is unknown or irrelevant.

### One Idea Per Sentence
Break complex thoughts:
- ❌ "The server validates configs and provides caching which respects API limits while supporting multiple versions."
- ✅ "The server validates configs against actual schemas. It includes a 15-minute smart cache. Every tool accepts explicit version parameters."

## Word Choice Patterns

### Simple Over Complex
| Instead of | Use |
|------------|-----|
| utilize | use |
| facilitate | help |
| leverage | use |
| implement | add/create |
| initialize | start |
| terminate | stop/kill |
| subsequently | then |
| approximately | about |

### Specific Over Vague
| Vague | Specific |
|-------|----------|
| a while | 30 minutes |
| several | 3 files |
| recent | v0.24.0 |
| many | 71% |
| large | 10k+ lines |

### Concrete Over Abstract
- ❌ "The tool provides enhanced capabilities"
- ✅ "The tool validates YAML in real-time"
- ❌ "Significant time savings"
- ✅ "Save 30-60 minutes per config"

## Structural Patterns

### Standard Blog Structure

```
1. Hero Image (full width)
2. CSS styling block
3. Bold subtitle/hook
4. Opening problem (2-3 paragraphs)
5. <!--truncate-->
6. Problem elaboration with data
7. Solution introduction
8. Deep dive with examples
9. Practical application
10. Resources and closing CTA
```

### Opening Hooks (Pattern Analysis)

**Pattern 1: Problem Statement**
"You ask an AI to generate... Nothing works."
- Direct second person
- Action → Failed result
- Immediate relatability

**Pattern 2: Time Investment**
"Ever spent hours... only to discover..."
- Universal experience
- Effort → Disappointment
- Creates empathy

**Pattern 3: Reframing**
"The question isn't whether... It's how..."
- Shifts perspective
- Assumes acceptance
- Focuses on execution

### Section Headers

Use active, specific headers:
- ✅ "The Cost of Hallucinated Configs"
- ✅ "Making AI Reliable for vCluster Configs"
- ✅ "Try It Now (2 Minutes)"
- ❌ "Introduction"
- ❌ "Implementation Details"
- ❌ "Conclusion"

### Transitions Between Sections

Natural flow patterns:
- Problem → Impact: "This isn't just inconvenient—it's expensive."
- Impact → Solution: "Stop hallucinations by grounding AI in actual schemas."
- Solution → Proof: "How it works:"
- Proof → Action: "Try it now:"

## Technical Content Patterns

### Code Block Presentation

**Always provide context:**
```
[What this does and why]

\`\`\`language
code here
\`\`\`

[Result or next step]
```

**Example:**
```
Query specific versions without state conflicts:

\`\`\`bash
vcluster-yaml query "sync.fromHost" --version v0.24.0
\`\`\`

Returns the exact schema for that version.
```

### Command Examples

Show realistic usage:
- Include comments explaining flags
- Show expected output
- Provide alternatives
- Add error handling patterns

**Pattern:**
```bash
# Interactive selection
just blog-diagrams

# Or specific file
python3 scripts/__process_blog_mermaid.py blog/my-post.mdx
```

### Technical Explanations

Layer complexity:

**Level 1 (What it does):**
"Fetches configs directly from GitHub."

**Level 2 (How it helps):**
"Every query validates against actual schemas—no pattern matching."

**Level 3 (Technical details):**
"Uses a 15-minute smart cache that respects GitHub API rate limits."

Start with Level 1, add Level 2 for context, include Level 3 only when relevant.

## Visual Content Integration

### DataGrid Usage

Use for structured comparison data:
- Metrics and values
- Before/after comparisons
- Feature matrices
- Statistics with impact

**When to use:**
- 3+ data points to compare
- Need for scannable info
- Impact visualization
- Badge highlighting important values

### InfoCards Usage

Use for feature lists:
- Tool capabilities
- System components
- Platform comparisons
- Process steps

**When to use:**
- 2-4 distinct items
- Equal importance items
- Need for visual separation
- Feature highlighting

### Diagrams

Use when:
- System architecture needs visualization
- Process flow isn't linear
- Multiple components interact
- Text explanation would be verbose

**Keep diagrams:**
- Simple (5-7 nodes max)
- One concept per diagram
- Dark theme (site consistency)
- With descriptive alt text

## Paragraph Structure

### Opening Paragraphs
2-3 sentences establishing problem:
1. Hook (provocative statement or question)
2. Context (why it matters)
3. Promise (what they'll learn)

### Body Paragraphs
Standard pattern:
1. Topic sentence (main idea)
2. Supporting detail or example
3. Implication or connection to next idea

### Closing Paragraphs
2-3 sentences:
1. Summarize key point
2. Call to action
3. Invitation to engage

## Lists and Formatting

### Bulleted Lists
Use when:
- Items don't have sequential order
- 3-7 related points
- Quick scanning needed

**Pattern:**
- Start each with same part of speech
- Keep items parallel in structure
- One idea per bullet
- Sub-bullets only when necessary

### Numbered Lists
Use when:
- Steps must be followed in order
- Ranking or priority matters
- References needed ("As mentioned in #3...")

### Bold Text
Use for:
- Key terms (first mention)
- Section emphasis ("What it does:**)
- Important warnings
- Never for entire sentences

### Code Formatting
Use backticks for:
- Commands: `kubectl get pods`
- File paths: `blog/_media/`
- Code elements: `--version` flag
- Technical terms: `mermaid` syntax

## Data and Statistics

### Presenting Numbers

**With context:**
- ✅ "71% of companies use generative AI"
- ❌ "Most companies use AI"

**With impact:**
- ✅ "Save 30-60 minutes per config"
- ❌ "Saves significant time"

**With source:**
- ✅ "According to [source]..."
- ❌ "Studies show..."

### Tables vs. DataGrid

**Use tables for:**
- Simple data (2-3 columns)
- Text-heavy comparisons
- Markdown-only content

**Use DataGrid for:**
- Visual impact needed
- Badge highlighting
- Interactive sorting
- 4+ columns

## Link Integration

### First Mention Links
Link technical terms on first mention:
- ✅ "[AI hallucination](url)" (first time)
- ✅ "AI hallucination" (subsequent)

### Resource Links
Make descriptive:
- ✅ "[GitHub repo](url)"
- ✅ "[MCP specification](url)"
- ❌ "[click here](url)"
- ❌ "[link](url)"

### External Citations
Always verify and use authoritative sources:
- Official documentation
- GitHub repositories
- Industry standards
- Academic papers
- Reputable tech blogs

## Common Pitfalls to Avoid

### Verbose Generalizations
❌ "In conclusion, we've explored the various aspects of this fascinating topic and learned about the many different ways to approach this common problem in modern software development."

✅ "Try it. Let me know what breaks."

### Over-Qualification
❌ "This might potentially help you in some cases"
✅ "This helps you validate configs"

### Passive Academic Voice
❌ "It has been observed that configs are often generated incorrectly"
✅ "AI generates incorrect configs"

### Unnecessary Complexity
❌ "Utilize the aforementioned methodology"
✅ "Use this method"

### Empty Adjectives
❌ "incredibly powerful amazing tool"
✅ "validates 100+ fields per second"

## Closing Patterns

### Standard Closing Template

```markdown
---

[Call to action with personality]

🔗 **Connect with me on** [**LinkedIn**](url)
🌐 **Visit my** [**Website**](url)
📺 **Subscribe to my** [**YouTube Channel**](url)
```

### CTA Variations

**Experimental:**
"Try it. Let me know what breaks. Star it if it saves you time."

**Collaborative:**
"Try it. Share your results. Contribute if you find it useful."

**Invitational:**
"Get started. Join the discussion. PRs welcome."

**Pattern:** Brief. Direct. Action-oriented.

## Voice Consistency Checklist

- [ ] Active voice (80%+ of sentences)
- [ ] "You" addressing reader
- [ ] Personal perspective ("I built", "I use")
- [ ] Short sentences (avg 15-20 words)
- [ ] Simple words (8th grade reading level)
- [ ] Specific numbers (not "many", "several")
- [ ] No hedging ("helps" not "might help")
- [ ] Problem-first opening
- [ ] Code examples with context
- [ ] Closing CTA

## Quick Style Reference

**Sentence Length:** 15-20 words average, mix short/long
**Paragraph Length:** 2-4 sentences, occasionally single sentence for impact
**Section Length:** 3-6 paragraphs, break longer sections
**Code Blocks:** Always specify language, add context before/after
**Links:** Verify all, descriptive text, first mention for terms
**Bold:** Key terms only, never full sentences
**Lists:** 3-7 items, parallel structure, one idea per point

Remember: Write for a competent technical reader who values their time. Show, don't tell. Be direct, be clear, be useful.
