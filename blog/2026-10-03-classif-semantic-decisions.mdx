A script can find `token` in a diff. A text match cannot tell whether it means an API credential, a model's context budget, or a parser token.

I built [classif](https://github.com/Piotr1215/classif) to let scripts ask about meaning. It takes text and a question, then returns a label, score, and exit code that the program can act on.

<!--truncate-->

## A question inside a shell pipeline

You can use it to select changes for a security review:

```bash
git diff --staged |
  classif -p "Does this change handle secrets, credentials or who may access what?" |
  ifne claude -p "Review this for security"
```

`git` supplies the diff. `classif -p` passes it unchanged when `yes` wins and emits nothing otherwise. `ifne`, from moreutils, starts the reviewer only when it receives input.

The question can catch an access change without the word `permission`, or leave a change about model tokens alone.

In checks on real dotfiles patches, a keyword filter selected an AI model streaming change that contained `token` seven times; classif answered `no`. A patch adding secret creation to a picker passed through byte for byte.

A backup patch scored close to a tie until I included the commit's explanation. The answer depends on the evidence supplied. These checks covered a few patches and had no independent accuracy rating.

The pipeline hides classif's exit status. A review workflow needs a separate route for failed or uncertain decisions.

## How it grew

The idea came from Jev's semantic decisions for programs and SemIf-OpenJev's one-token scoring approach. My first implementation appeared on 23 September as `class`.

It used a small local model to filter retrieved memories and repository snippets for AI sessions. I removed the filter because it saw only the prompt; the session had the conversation needed to judge relevance.

The tool expanded to relevance questions, change categories, feedback policies, and document questions. Each asks a program to interpret text and choose among a few answers. The public name became `classif`, combining classification with `if`.

classif supplies a small semantic operation. The caller collects data, keeps state, retries, and acts on the answer.

## Small answers that code can use

The default answers are `yes`, `no`, and `unknown`. You can also supply named options with descriptions:

```bash
printf '%s\n' 'Fix a startup crash.' |
  classif "What kind of change is this?" \
    -e "bug=repairs broken behavior" \
    -e "feature=adds a capability" \
    -e "chore=maintenance with no behavior change"
```

The descriptions guide the decision; the script receives the option name. A policy file can supply rules for the decision.

For short input, classif asks the model for one answer token. A score floor lets the caller withhold weak answers. `unknown` means the text does not settle the question. Even a high score needs checking against the evidence.

## Long text changed the problem

The first shell helper handled small inputs. Longer documents exceeded one model context.

An early passage could suggest an answer that a later passage overturned. Reading everything fixed some omissions but could take minutes and still yield no answer.

Searching for evidence first brought the biggest improvement. classif keeps the source outside the model's context, selects passages, and falls back to a broader read when needed. This draws on Recursive Language Models, which let a model inspect long input in smaller steps.

One matched test asked whether Elizabeth dies in *Pride and Prejudice*. The earlier version took 4 minutes 21 seconds and returned `insufficient`. The search version answered `no` in 17 seconds on a cold run, then 3.9 seconds with the saved index.

These timings cover one question on my machine. Some questions require a full read, and the tool can give a wrong answer. A search result identifies the evidence it found but cannot establish that no other passage changes the answer.

The [architecture document](https://github.com/Piotr1215/classif/blob/main/docs/architecture.md) has the reading plans, caches, diagrams, and full measurements.

## Try it locally

classif uses Python and Ollama. My first Hugging Face model repository contains a [Q4_K_M quantization of Winnow-12B](https://huggingface.co/Piotr1215/Winnow-12B-GGUF), saving the larger BF16 download and a local quantization build.

The [quick start](https://github.com/Piotr1215/classif#quick-start) covers model setup and alternatives. Once the model is ready:

```bash
git clone https://github.com/Piotr1215/classif.git
cd classif

./classif "Is this about Kubernetes?" "The pod keeps crashlooping."
```

My run returned `yes 0.95`. Try a question on text your script already handles: a diff, a comment, or a log.
